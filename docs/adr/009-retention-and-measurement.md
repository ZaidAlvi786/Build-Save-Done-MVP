# ADR 009: Opted-in digest and authoritative reminder metric

Status: accepted for Phase 4 local implementation, 2026-10-13.

Use PostHog's HTTP batch API through an authenticated Supabase Edge function. This keeps its project token off the client and needs no new dependency. The app explicitly opts in, persists only the eight allowlisted events in account-bound SQLite, retries with stable UUIDs, and discards acknowledged or older-than-30-day events. Limit the queue to 1,000 rows and uploads to 20 events per request and 1,000 events per account/hour. There is no autocapture, session replay, screenshot, place text, email, push token or device position in event properties. PostHog uses the verified Auth ID as distinct_id and does not create person profiles. The funnel covers consenting, signed-in activity only.

Compute the product metric in Postgres from reminder actions, independently of analytics consent or delivery. Preserve first_saved_at on users when the first server save is inserted, including pending saves. Preserve the earliest Navigate/Been there action in its seven-day window, using action_at so delayed offline replies qualify. Both timestamps survive deletion of individual saves/reminders. Account deletion removes the cohort identity and aggregate contribution. Only completed seven-day cohorts enter the denominator; the window is [first save, first save + seven days). Empty cohorts have a null rate and target_met=false. Target is at least 15%, not a claim about real adoption. Device clocks and permanently unsynced/deleted offline actions remain limitations.

For the digest, choose Friday 18:00 in the installation's IANA time zone, a 5 km radius and six-hour freshness. Explicit consent uploads only IDs of confirmed, unvisited nearby destinations selected on the phone during foreground checks. IDs still reveal coarse proximity, so disclose that separately. Never upload continuous location. Default off; newest explicit enable owns one installation. A compare-and-set refresh prevents older installations taking ownership. Sign-out stops that installation's digest before removing authentication. In-flight pushes may still arrive.

Supabase Cron calls weekly-digest every ten minutes using a Vault-backed scheduler secret. Service-only row locks reserve each user's local week before the external call; sending is at most one attempt per week. Ambiguous failures can miss a digest and are not retried, avoiding duplicate pushes. Expo tickets and later receipts distinguish accepted, failed and unknown delivery; a successful receipt means handoff to FCM/APNs, not that the user saw it. Token-invalid replies disable only the token used by that lease. No paid service, cron, or remote deployment was provisioned locally.

Snooze means one notification 24 hours after the tap, regardless of whether the user is still nearby. It uses its own persisted reminder UUID and can itself be snoozed. Scheduling retries reuse that UUID. Future or canceled notifications do not upload a sent reminder. Pause, visit, deletion and sign-out cancel pending snoozes. OS delivery/reboot behavior requires physical validation.

Sources: [PostHog capture API](https://posthog.com/docs/api/capture), [Expo push sending and receipts](https://docs.expo.dev/push-notifications/sending-notifications/), [Expo notification API](https://docs.expo.dev/versions/latest/sdk/notifications/).
